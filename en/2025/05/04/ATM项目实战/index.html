项目实战：分层写一个 ATM 柜员机

前言

学完函数、装饰器、文件操作之后，基础班的收官项目是一个命令行 ATM：注册、登录、查余额、存款、取款、查流水。功能不复杂，但它第一次让我意识到「代码要分层写」——如果所有逻辑都堆在一个文件里，每加一个功能都要改动一堆地方。

这篇笔记完整记录这个项目的设计取舍和实现细节，最后也会诚实地复盘它的几个硬伤，以及后来学了面向对象和数据库之后怎么解。

一、要实现什么

序号 功能 说明
1 注册 用户名 + 密码 + 确认密码，密码不一致要重来；已存在的用户名不能重复注册
2 登录 用户名 + 密码，成功后记住登录状态
3 查询余额 需要登录
4 存款 需要登录，记一笔流水
5 取款 需要登录，余额不足要拒绝
6 查询流水 需要登录，按时间顺序打印
0 退出 结束程序

注册成功后初始余额是 10 元（方便测试存取款），数据用 JSON 文件保存——那时候还没学数据库。

二、目录结构：先分层，再写代码

调用链是单向的：

graph LR
    A[run.py 启动] --> B[core/src.py 门面
负责输入输出]
    B --> C[api/user_i.py
api/bank_i.py 业务逻辑]
    C --> D[DB/db_handle.py
读写 JSON]
    D --> E[(DB/user_data/*.json)]
    B -.装饰器拦截.-> F[lib/common.py
is_login]

各层只做一件事：门面层负责和用户对话，业务层负责判断和计算，数据层负责存取，配置层负责路径。这样换存储方式（JSON → MySQL）时，只需要重写数据层。

2. 门面层：用字典代替一堆 if

最初功能菜单是这么写的：

功能一多，这个 if 链就越长越难改。课程里教了一个更清爽的写法：把「序号 → 功能」做成字典，循环遍历打印菜单，再用序号直接取出函数调用。

两个容易写错的地方：

  1. 字典里的函数不能加括号——"注册": register 是「存这个函数」，写成 register() 就变成「立刻调用并把返回值存进去」；
  2. 用户输入要转成 int 再判断，否则 '1' in fun_select 永远是 False（键是整数）。

这样加功能只需要在字典里加一行，菜单会自动多出一项。

五、复盘：这个项目的五个硬伤

项目能跑，但离「像样」还差得远。把它当作一次体检，问题正好对应后面要学的知识：

问题 现象 后来的解法
密码明文存储 JSON 里能直接看到 666666 高级编程班的项目里用 hashlib.sha1 加盐/哈希存密码（Django 项目用的是自定义 gen_sha1_pwd）
用全局变量记录登录态 login_user 谁都能改，多用户场景会串号 面向对象：把状态收进对象的属性里；Web 里则用 session
没有输入校验 存款时输入「abc」，float() 直接抛异常退出 异常处理 try/except + 循环重试
JSON 文件不是数据库 没有并发保护、没有事务、无法按条件查询 MySQL：表结构、约束、事务
逻辑全在函数里 功能多了以后参数越传越长 面向对象：类封装数据与行为

最值得记住的一条是分层：正是因为它把「用户界面 / 业务判断 / 数据存取」拆开了，上面这些问题才能一个个单独替换——换存储只动 DB/，换交互只动 core/。

小结

这个项目教会我的三件事：用字典做分发让菜单可扩展、用装饰器做拦截让校验不重复、用相对路径反推项目根目录让代码可以在任何电脑上跑。而它暴露的问题，恰好就是高级编程班要解决的——面向对象、异常处理、数据库，下一篇就接着写。

说明：这是基础班（玫玫老师）的收官项目，代码来自课堂，我按自己的理解补了注释与复盘。
