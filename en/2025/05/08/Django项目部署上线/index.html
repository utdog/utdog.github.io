Django 项目部署上线：uwsgi + nginx + conda 实战

前言

本地 python manage.py runserver 能跑，和「别人能访问」是两件事。这是 Django 班的最后一课：把 single_blog 部署到一台阿里云 ECS（Ubuntu/CentOS）上。整个过程我踩的坑大多不在 Django 本身，而在nginx 编译依赖、静态文件路径、云服务器安全组这三处。

这篇笔记按实际部署顺序记录，配置都来自课程课件，可以直接对照。

一、先把三个名字分清：WSGI / uwsgi / uWSGI

课件开篇专门强调这一点，因为这三个词差一个字母，含义完全不同：

名称 是什么
WSGI Web Server Gateway Interface，Python PEP333 提出的通信协议规范，约定 wsgi server 怎么调用 web 应用
uwsgi 一种线路协议（不是通信协议），常用于 uWSGI 服务器与其他网络服务器之间的数据通信
uWSGI 一个Web 服务器，实现了 uwsgi 和 WSGI 两种协议

为什么需要 WSGI：Django、Flask 这些框架内部实现各不相同，如果没有统一规范，服务器就得为每个框架写一套适配；有了 WSGI，只要双方都遵守协议，应用和服务器就能随意组合。

nginx 与 uWSGI 的完整交互流程：

graph TD
    A[浏览器] -->|HTTP 请求| B[nginx 80/8888]
    B -->|静态文件| C[直接返回 static 目录]
    B -->|动态请求 uwsgi_pass| D[uWSGI 8080]
    D --> E[WSGI]
    E --> F[Django 视图]
    F --> E --> D --> B --> A

六步：① nginx 作为对外的服务接口接收 HTTP 请求，解包分析；② 静态文件请求，nginx 按配置目录直接返回；③ 动态请求通过配置转发给 uWSGI；④ uWSGI 处理后再转给 WSGI，WSGI 调用 Django 的某个视图函数；⑤ Django 返回结果交给 WSGI 打包，再回给 uWSGI；⑥ uWSGI 回给 nginx，nginx 最终返回给浏览器。

nginx 负责静态文件和反向代理，uWSGI 负责跑 Python 应用——这就是典型的动静分离。

要注意的几个细节（课件里都踩过）：

  • DjangoUeditor 是用 python setup.py install 装进 site-packages 的，服务器上要么重新安装，要么把本地 site-packages/DjangoUeditor 整个目录复制到服务器的相同位置；
  • haystack 的中文检索改过源码（ChineseAnalyzer.py、whoosh_cn_backend.py），这两个文件也要一起复制到服务器 site-packages 的对应目录，否则线上搜不到中文。

九、常见故障速查

现象 可能原因 处理
502 Bad Gateway uwsgi 没起来 / uwsgi_pass 端口不对 ps aux | grep uwsgi，看 uwsgi.log
页面样式全丢 collectstatic 没做或 STATIC_ROOT 不对 重跑 collectstatic，检查 nginx alias
改代码不生效 没重启 uwsgi uwsgi --stop uwsgi.pid 后再 --ini 启动
外网访问不了，本机 curl 正常 安全组/防火墙 控制台放行端口
configure: error 缺库 PCRE / zlib / openssl 按上表装依赖
上传的图片 404，缩略图不显示 路径按 BASE_DIR 拼接 改成按 STATIC_ROOT 拼，见第六节
中文搜索无结果 haystack 改了源码没同步到服务器 复制 ChineseAnalyzer.py、whoosh_cn_backend.py

小结

部署这一课的价值不在于记住命令，而在于理解**「谁负责哪一段」**：nginx 管对外的端口、静态文件和反向代理，uWSGI 管跑 Python 应用，WSGI 是两者之间的约定，Django 只管业务逻辑。想通这条链路之后，502、静态 404、端口不通这三类报错就都能对号入座了。

顺带一提，本博客（Hexo 静态站点）的部署和这里是两条完全不同的路：它没有「应用进程」，hexo generate 出的就是纯静态文件，推到 GitHub Pages 即可，不需要 uwsgi 和 nginx。动态站点部署的是进程，静态站点部署的是文件——这句话是我学完这一课最直观的收获。
