Python 网络编程：从 socket 到 IO 多路复用

前言

此前的项目（比如 ATM）都跑在一台机器上，学完网络编程才算能写「两个程序隔着网络对话」的东西。这一课的主线是：先用 socket 把 TCP 通信跑通 → 发现粘包 → 用 struct 定长报头解决 → 发现阻塞导致只能服务一个客户端 → 用非阻塞轮询 → 最后用 select 让内核帮忙等。每一步都是被上一步的问题逼出来的，这条思路比记住 API 更值得写下来。

一、几个必须分清的基础概念

概念 要点
OSI 七层 / TCP-IP 四层 应用层、传输层、网络层、网络接口层（TCP/IP 视角）；HTTP 在应用层，TCP/UDP 在传输层
IP + 端口 IP 定位主机，端口定位进程；1024 以下是系统保留端口，程序一般用 1024–65535
C/S 与 B/S C/S 需要装客户端（QQ）；B/S 用浏览器就行（网站），本质还是 C/S，浏览器就是客户端
TCP vs UDP TCP 面向连接、可靠、流式、有粘包；UDP 无连接、不可靠、保留消息边界、不粘包

socket 是应用层与 TCP/IP 协议族之间的中间软件抽象层：它把复杂的协议细节藏在接口后面，我们只要按它的规定调用就行。

二、TCP 通信：服务端七步、客户端四步

几个容易搞错的点：

  1. accept() 有两个返回值：conn 是新的套接字对象（专门用于和这个客户端通信），client 是客户端的 (ip, port)；后续收发用的都是 conn，root 只负责迎接新连接；
  2. send 只接受 bytes，字符串必须 .encode()；
  3. bind 的参数必须是元组，写成 bind('127.0.0.1', 10086) 会直接报错；
  4. 收发的两端要配合：如果双方都先 recv 再 send，就会互相等，形成死锁——一端先发、另一端先收。

三、粘包：TCP 是「流」，没有消息边界

写一个「远程执行命令」的版本就会立刻撞上粘包：

客户端用 recv(1024) 接收，结果只拿到前半截，下一次又拿到剩下的部分——这就是粘包。原因不是 TCP「坏了」，而是：

  • TCP 是面向字节流的协议，没有「消息边界」概念。发送端两次 send 的数据可能被合并成一个包发出去（粘包），一个大数据也可能被拆成多个包（拆包）；
  • 接收端 recv(1024) 只保证「最多收 1024 字节」，不保证收满。

解决思路：给数据加一个「固定长度的报头」，里写明后面正文有多少字节。

三个必须理解的细节：

  • struct.pack('i', n) 是固定的 4 字节（i 表示 int），所以接收端可以先 recv(4) 拿到确定长度；用 struct.unpack('i', header)[0] 解回来（返回的是元组，要取 [0]）；
  • 不能直接 recv(total_size)：TCP 不保证一次给你这么多，所以必须用 while recv_size < total_size 循环累加；
  • Windows 上命令结果是 GBK 编码，服务端打印和客户端解码都要用 gbk，否则中文全是乱码。

课件里还给了另一个版本：每次限制读取 1024 字节（min(剩余长度, 1024)），本质一样，是把「一次最多读多少」也显式算出来。

四、阻塞：为什么服务端只能服务一个人

默认情况下 socket 的 accept() 和 recv() 都是阻塞的——没有连接、没有数据时，程序就停在那里等。想让它不等待，就设置成非阻塞：

变成非阻塞之后，一旦 accept/recv 没有就绪的 IO，就会抛 BlockingIOError。注意：这不是代码写错了，而是非阻塞模式下没有 IO 请求时的固定行为。

用课堂上的话解释就是：十个客户，难道一个客户不回信息你就傻等吗？当然是去处理别人的问题。

但这个写法有两个明显缺点：

  1. CPU 空转：while True 不停问「有数据吗」，没数据就抛异常再问一遍，白烧 CPU；
  2. 要自己维护连接列表：谁断开、谁还在，都得手动管。

五、IO 多路复用：让内核替你等

select 的思路是「同时监控多个 IO 事件，哪个就绪就处理哪个」，等待这件事交给操作系统内核做，程序只在有事时被唤醒。

三个关键点：

  • select.select(rlist, wlist, xlist) 分别监控「可读、可写、异常」三类事件，返回三个就绪列表；我们只关心可读，所以后两个传空列表；
  • read is root 用 is 判断是不是同一个对象（内存地址相同）：是监听套接字就去 accept，否则就是客户端套接字，直接 recv；
  • recv 返回空 bytes 表示对端已关闭，这时必须 close() 并从列表移除，否则下一轮 select 还会一直报告它「可读」，形成死循环。

非阻塞轮询 vs select

维度 非阻塞轮询 select 多路复用
谁来「等」 程序自己不停问 内核，就绪才返回
CPU 占用 高（空转） 低
代码复杂度 要处理异常 + 手动遍历 只处理返回的就绪列表
连接数上限 自己维护列表 select 有 fd 数量上限（通常 1024）
适用场景 学习理解「阻塞/非阻塞」 中小规模并发连接

课件到这里结束。再往上就是 poll 和 epoll（Linux 下更高效的事件通知机制）以及 asyncio（协程版异步 IO），课程没有涉及，我还没有系统学过，就不在这里硬写了。

六、踩坑记录

现象 原因 解决
OSError: [WinError 10048] 地址已在使用 端口被占用（上次的程序没退干净） 换端口，或在任务管理器结束残留 python 进程
ConnectionResetError 客户端强制关闭（关机、杀进程） 服务端 try/except 捕获后 break 跳出该连接的循环
中文乱码 Windows 命令输出是 GBK，代码里用 utf-8 解 打印/解码统一用 gbk
只收到一半数据 TCP 粘包/拆包 加 struct 定长报头 + 循环接收
服务端只能连一个客户端 accept/recv 阻塞 非阻塞 + 轮询，或 select
select 一直返回某个已关闭的连接 没有在收到空数据时移除它 收到空 bytes 立即 close() 并 remove()
两端互相卡住 双方都先 recv 明确谁先发、谁先收

小结

这一课真正学到的是**「问题驱动」的思路**：单客户端够用 → 想服务多人 → 阻塞成了障碍 → 非阻塞轮询 → 轮询浪费 CPU → 交给内核（select）。每一步的技术选择都是被上一个问题推出来的。

顺带一句：本文的所有代码都来自课堂源码（day11网络编程+socket编程、day12非阻塞+io多路复用）与课件讲义（07–12），我只做了注释补充和排版整理。下一篇写并发编程——进程、线程、锁、进程池和协程，那里会看到「同样想同时处理多件事」的另外几种解法。
