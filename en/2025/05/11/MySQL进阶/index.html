MySQL 进阶：外键、视图、存储过程、触发器与事务

前言

基础篇解决的是「怎么把数据存进去、查出来」，进阶篇解决的是**「怎么让数据库自己保证数据是对的、并且扛得住用」**：用外键约束保住关联完整性、用视图简化复杂查询、用存储过程和触发器把逻辑下沉到数据库、用事务保证一组操作要么全成功要么全失败，最后还要考虑范式、存储引擎和拆表。

这篇按课程（课件《19-MySQL进阶》+ day06–day10 笔记）的顺序整理，示例沿用课上的部门/员工、学生/班级那几张表。

一、外键约束与三种表关系

外键的完整语法还带级联动作：

级联动作 主表删除记录时 主表改主键值时
RESTRICT（默认） 从表有关联记录则不允许删除 从表有关联则不允许修改
CASCADE 从表相关记录一起删除 从表外键值级联更新
SET NULL 从表外键字段变为 NULL 从表外键字段变为 NULL

用外键时课件总结了四条顺序上的注意点（踩过就知道）：

  1. 先创建被关联的表，再创建带外键的表；
  2. 先插入被关联表的数据，再插入带外键的数据；
  3. 外键字段的值只能是被关联表中已存在的值；
  4. 修改/删除要先处理外键字段（或者依赖级联动作）。

三种表关系怎么表达

记住这个对应关系：一对一把唯一约束加在外键上，一对多把外键放在多的一方，多对多靠中间表。

这条语句不会「智能匹配」，而是把 A 表每条记录和 B 表每条记录强行拼起来——所以 n 条 × m 条就会返回 n×m 条，这就是笛卡尔积。想要正确结果，得在 where 里补上关联条件，或者直接用连接语法（官方更推荐后者）：

一句话区分：内连接是「交集」，左/右连接是「保留某一侧的全部，另一侧没有就补 NULL」。「查出没有部门的员工」就要用左连接 + where b.id is null。

三、视图：只存定义，不存数据

视图是一张虚拟表：有行有列，但数据库里只存它的定义，数据仍然来自它引用的真实表；真实表一变，视图查出来的结果跟着变。

课件的两点提醒很关键：

  • 视图的增删改查和普通表一样，但真实表的约束（非空、唯一、外键）依然生效；
  • 视图的价值在于筛选与安全：可以把用户不需要、或者不该看到的列屏蔽掉，对外只暴露一个视图。

视图的四个典型作用：简化复杂查询、数据安全性、数据抽象、重用性。

四、函数与存储过程

两者都是「把编译好的 SQL 存进数据库，用的时候调用」，区别在于：

函数 存储过程
返回值 有且只有一个 不能有返回值（返回结果集）
参数 只有输入参数 可以有 in / out / inout
调用方式 可以作为查询语句的一部分，select f1() 独立执行，call p1()
侧重 计算并返回一个值 执行一套流程

为什么要写 delimiter

如果不改结束符，MySQL 一看到 begin 里面第一个 ; 就以为「语句结束了」，定义会被截断。delimiter 就是给整个函数/过程让路的临时结束符。

存储过程与三种参数

三种参数的区别（课件原话整理）：

  • in：可以接变量或常量，内部随便用，修改传不回外部；
  • out：只能接一个变量，内部不能使用它原本的值（进来是 NULL），但可以把结果写进去，外部能拿到；
  • inout：既能读原值，也能把修改带出去。

配套的管理语句：

触发器：事件驱动的 SQL

触发器的特点是不由程序调用，也不手动执行，而是对某张表做 insert/update/delete 时自动激活——课件用「打开开关，灯就亮」来类比。

  • 触发时间：before（动作之前）/ after（动作之后）
  • 触发条件：insert / update / delete
  • new：新增或修改时的新数据；old：修改或删除时的旧数据
  • for each row：固定写法，表示每行都触发

课上那个例子很实用——新增一个学生，班级人数自动 +1：

触发器的优点是自动执行、级联更新、强化约束、跟踪变化、强制业务规则；代价是逻辑藏在数据库里，排查问题时不容易发现，而且触发器里再写触发器会让链路变得难以追踪。所以工程上常用「业务层显式处理」替代复杂触发器。

五、事务与隔离级别

事务是一组要么都执行、要么都不执行的 SQL 命令序列，典型场景就是订票、银行转账。

ACID 四大特性（课件定义）：

  • 原子性：事务中的操作是一个不可分割的整体，要么全成功要么全失败；
  • 一致性：事务前后数据都要处于一致状态，不能损坏数据；
  • 隔离性：并发事务之间互不干扰；
  • 持久性：提交后的修改永久保存，即使系统故障也不丢。

隔离性是四个里最容易出问题的，因为隔离级别不同，能观察到的并发现象也不同：

隔离级别 能读到什么 会有什么问题
read uncommitted 读未提交 别人未提交的数据也能读到 脏读（级别最低，理论存在）
read committed 读已提交 别人提交后才能读到 避免脏读，但会不可重复读
repeatable read 可重复读 别人提交了也读不到，本事务内一致 MySQL 默认级别，但会有幻读
serializable 串行化 事务排队执行 避免幻读，但吞吐量太低

一句话记住三种现象：脏读=读到没提交的；不可重复读=同一事务里两次读结果不一样；幻读=同一查询两次返回的行数不一样。

六、数据库优化：范式、引擎、拆表

设计范式

范式 要求 课件例子
1NF 每一列都是不可再分的原子项 姓名在国内算原子；在国外要拆成 FIRST NAME / LAST NAME 才符合
2NF 每条记录能被唯一区分（有主键），所有属性依赖主属性 简单理解：给表设一个主键
3NF 属性之间不传递依赖，不包含其他表已有的非主键信息 合理使用外键，避免不同表里存重复字段

课件也点出了代价：范式越高冗余越小，但表拆得越细，多表连接的开销越大——所以工程上通常做到第三范式即可。

存储引擎

常用的两个：

InnoDB MyISAM
锁 行级锁（只锁指定记录） 表级锁（锁表期间别人不能写，写锁连读都不行）
事务/外键 支持事务、回滚、外键 不支持
文件 .frm 表结构 + .ibd 记录与索引 .frm 结构、.MYI 索引、.MYD 数据

选型结论（课件）：查操作多的表用 MyISAM，写操作多的表用 InnoDB。现在的新项目基本默认 InnoDB。

键的设置与表拆分

课件的四条建议：

  1. InnoDB 不设主键也会自建隐含主键，最好自己显式设置；
  2. 主键尽量选占用空间小的字段；
  3. 外键能保证完整性，但会降低导入和操作效率，高并发下要慎用；
  4. 不用外键时，也要在关联字段上建索引，否则连接查询会很慢。

表拆分的两种思路：

  • 垂直拆分：列太多就拆表，常查的放一起，blob/text 这类大字段单独放一张表；
  • 水平拆分：数据量太大就按关键字把行拆到多张表（分表/分库）。

八、踩坑记录

现象 原因 解决
Cannot add or update a child row: a foreign key constraint fails 外键值在被关联表里不存在 先插主表数据，或用 SET NULL/CASCADE
Cannot delete or update a parent row 从表还有关联记录（默认 RESTRICT） 先删从表，或设置级联动作
建函数/过程报语法错误 没改 delimiter，begin 里的 ; 被当成结束 定义前 delimiter $.，定义后改回 delimiter ;
out 参数拿不到值 没用变量接收，或忘记 select ... into 参数 set @v = 0; call p(@v); select @v;
触发器没生效 触发时间/条件写错（如把 after insert 写成 before delete） 按「时间 + 事件 + 表 + for each row」逐项核对
事务没回滚 用了 MyISAM 引擎，或不支持事务的语句 表改成 InnoDB，明确 begin/commit/rollback
别人没提交的数据我读到了 隔离级别是 read uncommitted 改成 read committed 及以上
代码里 SQL 拼接被注入 用 format/+ 拼 SQL 一律用 %s 参数化 + executemany

小结

进阶篇里我最想记住的是三句话：

  1. 外键的价值是「让数据库替你把关」，代价是插入顺序受限、并发下效率下降；
  2. 视图、函数、存储过程、触发器都是「把逻辑下沉到数据库」——它们能让应用层代码变简单，但逻辑一旦藏进数据库，排查和迁移都会变难，所以要克制使用；
  3. 事务的难点是隔离级别：默认的 repeatable read 在 MySQL 里够用，但要清楚它并不能避免幻读。
