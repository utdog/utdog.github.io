Study Log

面向对象讲完之后，还有两件事能让程序变得「不那么死板」：一件是让代码在运行时按字符串去操作对象，这叫反射；另一件是让程序在出错时不直接崩掉，这叫异常处理。这篇笔记把这两块放在一起整理。

本文依据课件《day04 反射和异常处理》的笔记与八份随堂代码整理，文末标了「补充」的部分是我自己加的。

先回顾一下继承

课件在这一天的开头先把前面三天的面向对象串了一遍，几个容易记混的点值得再写一遍：

场景 写法 注意
单继承 class B(A): 子类自动拥有父类的属性与方法
多层继承 class B(A)，A(S) 子类若写了 __init__，会覆盖爷爷类的，需要 super().__init__(money) 才能同时初始化
方法重写 子类定义同名方法 想在重写的方法里用父类的实现，写 super().sleep()
多继承 class C(A, B): 多个父类有同名方法时遵循从左到右的就近原则，所以「尽量避免多继承」
多继承的顺序 print(d.__mro__) super() 找的不是「写在外面的父类顺序」，而是 Python 用 MRO 算法算出来的顺序

一、反射：用字符串操作对象

课件的类比很形象：玩游戏时，没有反射是一条命只能选一个角色；有反射就能在游戏中途切角色。

反射的定义是：通过字符串的形式去操作对象的属性和方法。以前我们操作属性必须 对象.属性名 写死在代码里，反射让属性名可以在运行时才确定——比如来自用户的输入、来自配置文件的一行字符串。

四个反射函数

函数 作用 找不到时
getattr(object, name[, default]) 获取属性值或方法 给了 default 就返回它，否则抛 AttributeError
hasattr(object, name) 判断有没有这个属性 返回 True / False，不会报错
setattr(object, name, value) 设置属性值 没有该属性就新增一个
delattr(object, name) 删除属性 没有该属性抛 AttributeError

二、动态导入模块：importlib

importlib 是 Python 用来按字符串路径动态导入模块的模块。它的意义在于：模块名也可以来自配置、来自用户输入，而不是写死在 import 语句里。

两个要点：

  • importlib.import_module('datetime') 等价于 import datetime；写成 import_module('a.b.c') 时，等价于导入包路径 a.b 下的模块 c（也就是能用点号，但最小只能细到 .py 文件那一层，不能直接指到文件里的某个类或函数）；
  • 拿到模块对象之后，再用 getattr 取里面的属性/类，两者配合就能实现「字符串 → 模块 → 对象 → 方法」的全链路动态调用。

三、异常：让程序出错也不崩

课件用了这样一个类比：你规划好出门旅游三天，结果第二天老板叫你回去加班——计划中出现了预料之外的情况，这就是「异常」。

在 Python 里，异常指程序运行中出现的错误。不处理的话，程序会打印一大段 traceback 然后直接终止；异常处理就是把这些可预料的错误接住，让程序继续往下走。

基本语法：try / except

try 里放可能出错的代码，except 负责处理。想同时应付几种错误，就写多个 except：

补充（顺序）：多个 except 是从上往下匹配的，所以子类异常必须写在父类前面，否则父类会先把子类「吃掉」；要一次捕获多种，可以写成 except (ZeroDivisionError, ValueError):。而 except Exception: 虽然能兜住几乎所有错误，但它会把拼写错误、传参错误这类本该暴露的 bug 一起吞掉，只适合用在最外层「兜底 + 记日志」。

else 和 finally

这两个分支常被忽略，但很实用：

执行顺序可以这样记：

flowchart TD
    A[进入 try] --> B{try 里出错了吗}
    B -- 没出错 --> C[执行 else]
    B -- 出错了 --> D{能匹配到 except}
    D -- 能 --> E[执行 except]
    D -- 不能 --> F[异常继续向上抛]
    C --> G[执行 finally]
    E --> G
    F --> G
    G --> H[结束]

else 的用处是把「只有成功才做的事」和「可能出错的代码」分开，避免把后续逻辑也塞进 try 里被误捕获；finally 的典型用途是释放资源：关文件、关数据库连接、释放锁——不管中间有没有出错，这些收尾动作都必须执行。

常见的异常类型

课件列了六种，我再补几个写代码时最常撞见的，凑成一张速查表：

异常 什么时候出现
ZeroDivisionError 除数为零
NameError 使用了未定义的变量
TypeError 数据类型不匹配，比如 'a' + 1
ValueError 类型对但值不合法，比如 int('abc')
IndexError 索引越界
KeyError 字典里取不存在的键
AttributeError 对象没有这个属性/方法（反射报错就是它）
FileNotFoundError 打开的文件不存在
ModuleNotFoundError 导入的模块不存在
IndentationError / SyntaxError 缩进或语法错误（这类错误在运行前就会暴露，try 也接不住）

断言是给开发和调试用的：写代码时把「我认为这里一定成立」的假设写下来，一旦不成立就能立刻发现。运行 Python 时加 -O 选项（python -O demo.py）会关闭所有断言，所以它不适合承担真正的业务校验——用户的输入该用 if 判断，该抛异常就抛异常。

五、自定义异常

Python 内置的异常类型不够用时，可以自己定义，好处是报错信息更清楚、更容易定位：

四步套路：继承 Exception → 在 __init__ 里把消息交给 super().__init__() → 用 raise 抛出 → 用 except 自定义异常类 as e 接住并打印。

补充（两点）：① 课件的异常消息写成了「自定义异常文件的第 8 行出现错误：参数不能为负数」，把行号写死在消息里是很脆的写法——代码一改行号就过期，消息应该描述问题本身；② 自定义异常最好按业务划分层级（比如先定义 class AppError(Exception)，再让 UserNotFound(AppError)、OrderClosed(AppError) 继承它），这样上层可以「粗粒度兜底、细粒度分别处理」，还能用 raise MyError('...') from e 保留原始错误链，排查时看到完整的因果。

踩坑记

现象 原因 处理
AttributeError: x 对实例 delattr 一个类属性 类属性用 del 类名.属性；实例属性才归 delattr
setattr 改了类属性却不生效 它是在实例上新建同名属性做遮挡 打印 对象.__dict__ 与 类.__dict__ 对照确认
getattr(w, choose) 没反应 只取到了绑定方法没调用 补一对括号 getattr(w, choose)()
TypeError: ... is not callable getattr 取到的是普通属性（值），当方法调用了 先 callable() 判断，或换成白名单映射
用户输入导致程序暴露内部结构 反射时未做白名单校验 先校验名字属于允许集合，再反射调用
ModuleNotFoundError 来自 import_module 字符串里的模块名或路径层级写错 路径最小只能到 .py 文件，且要在 sys.path 里能找到
异常没被接住，程序照样退出 try 的范围没包住出错的那行 把可能出错的操作放进 try，而不是放进 else
except Exception: pass 之后 bug 找不到 静默吞掉了异常 至少 print(e) 或记录日志，必要时 raise 重新抛出
加了 -O 后断言失效 断言会被优化掉 业务校验用 if + raise，别用 assert
finally 里 return 覆盖了结果 finally 一定会执行，会吃掉前面的返回值 别在 finally 里写 return

小结

这一篇把课件最后一块内容收完了：

  • 反射解决「名字要到运行时才知道」的问题，核心是 getattr / hasattr / setattr / delattr 四个函数，配合 importlib.import_module 能把「模块 → 类 → 方法」整条链路都变成字符串驱动；
  • 异常处理解决「出错不要崩」的问题，骨架是 try / except / else / finally，配套还有 assert 断言与自定义异常；
  • 两者共同的思路是把写死的结构变成可配置、可预判的结构：前者让调用灵活，后者让失败可控。
